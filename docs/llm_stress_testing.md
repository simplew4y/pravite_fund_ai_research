# 📝 LLM 压力测试与质量回归手册

本项目提供一套可重复运行的 LLM 压测脚本，同时覆盖性能、输出质量、证据溯源、
并发隔离和工具调用。所有请求、模型生成内容、流式分片、工具轨迹、评分细项与系统
指标都保存在本机，不依赖外部评测平台。

## 📝 快速开始

先做最小验证：

```bash
./scripts/run_llm_stress_test.sh --suite smoke
```

执行正式测试：

```bash
./scripts/run_llm_stress_test.sh \
  --suite full \
  --target proxy \
  --concurrency 1,2,4,8,16 \
  --requests-per-level 20
```

同时比较 LiteLLM 代理与 `FinSagent/config/production.yaml` 中的当前上游：

```bash
./scripts/run_llm_stress_test.sh --suite full --target both
```

长期稳定性测试示例：

```bash
./scripts/run_llm_stress_test.sh \
  --suite soak \
  --concurrency 8 \
  --duration-seconds 1800
```

脚本默认使用 `omnigent/.venv`，默认目标为 `http://127.0.0.1:4000/v1`，模型名从
当前 `production.yaml` 读取。API Key 只用于内存中的请求头，不写入报告、manifest
或压缩包。

## 📝 测试套件

| 套件 | 用途 | 内容 |
| --- | --- | --- |
| `smoke` | 上线前快速确认 | 模型列表、普通请求、流式请求、工具能力预检和两条质量用例 |
| `quality` | 内容回归 | 全部合成用例和本地真实证据用例，单并发运行 |
| `load` | 容量测试 | 按并发阶梯重复质量场景，不执行工具轨迹 |
| `tools` | 工具准确性 | 只读私募工具的选择、顺序、参数和工具后回答 |
| `full` | 正式验收 | 并发、质量、真实证据、流式、工具能力与本机指标 |
| `soak` | 长稳测试 | 在最高指定并发持续运行到时间或 Token 预算结束 |

正式压测默认执行并发 `1,2,4,8,16`，每档至少 20 个请求；如果质量场景更多，
脚本会确保每档请求数不少于场景数。`--max-total-tokens` 是成本/容量保护的软上限。

## 📝 当前项目场景

质量用例不只检查 HTTP 200，还会确定性检查：

- 中文、单行、JSON 字段与精确取值等指令遵循。
- 每个请求的唯一 nonce，检测并发响应串线或上下文污染。
- `chunk:`、`fact:`、`cell:`、`page:` evidence ID 的必需引用、白名单和禁止引用。
- 甲乙公司证据隔离、资料未覆盖时拒绝猜测、证据文本中的提示注入抵抗。
- 数值计算、输入证据完整性、明显思考过程及 `reasoning_content` 泄露。
- 从 `output/private_fund_datasets/*/meta/collection.sqlite3` 只读抽取真实 chunk，验证当前项目资料的溯源遵循。
- `private_fund_dataset_status`、`private_fund_dataset_search`、
  `private_fund_source_detail` 等只读工具的选择、参数与多步顺序。

工具测试只把模型产生的调用参数送入本地模拟器，不执行真实 MCP 工具，因此不会写入
Memo、研究节点、提醒、项目资料或生产数据库。未向模型声明任何写工具；模型若生成未
授权工具名，只会记录为失败。

## 📝 主要指标与门槛

| 维度 | 指标 | 默认门槛 |
| --- | --- | --- |
| 可用性 | 请求成功率、HTTP/超时错误 | `>= 98%` |
| 延迟 | 总延迟 p50/p95/p99、流式 TTFT p50/p95/p99 | 重点观察并发拐点 |
| 吞吐 | 每档 RPS、生成 token/s | 与并发增长趋势一起判断 |
| 退化 | 最高并发 p95 / 最低并发 p95 | `<= 3x` |
| 指令 | JSON/格式/数值/安全用例整项通过率 | `>= 85%` |
| 溯源 | 引用完整、合法且不跨公司 | `>= 90%` |
| 隔离 | 不出现其他请求 nonce | `100%` |
| 推理 | 不出现显式思考标记或 reasoning 字段 | `100%` |
| 工具 | 工具名、顺序、参数、最终回答整项准确率 | `>= 90%` |

`BLOCKED` 与 `FAIL` 含义不同：前者表示服务端能力未配置、无法完成该测试，后者表示能力
存在但结果没有达到门槛。两者都不会被当作通过。

## 📝 本地结果与分析方法

每次结果位于：

```text
output/llm_stress_runs/<run_id>/
```

关键文件：

| 文件 | 内容 |
| --- | --- |
| `summary.md` / `summary.json` | 结论、门槛、各并发指标 |
| `metrics.csv` | 并发、RPS、延迟、TTFT、token/s、质量率 |
| `requests.jsonl` / `responses.jsonl` | 完整输入与输出；不含请求头和 API Key |
| `responses/` | 按 request ID 保存的完整响应 envelope |
| `stream_chunks/` | 每个 SSE 分片、相对时间与 usage |
| `tool_traces/` | 多步工具调用、参数、本地模拟结果与最终回答 |
| `evidence_checks.jsonl` | 每条指令和引用规则的通过/失败明细 |
| `failures.jsonl` | 可直接定位的失败请求或工具轨迹 |
| `system_metrics.csv` | 本机相关服务 CPU、RSS 与进程数 |
| `provider_metrics.jsonl` | vLLM/LiteLLM 暴露时的队列、缓存和延迟指标 |
| `analysis_bundle.zip` | 可交给 Codex 分析的完整本地结果包 |

运行完成后，把控制台打印的 `analysis_bundle.zip` 绝对路径发给 Codex，即可进一步分析
容量拐点、失败聚类、质量退化和建议上线并发。压缩包可能含真实研究资料片段，只应在
可信本地环境使用，不应上传到公共工单或公开仓库。
